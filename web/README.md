# web

피그마 [타래 UI](https://www.figma.com/design/Y5ZZ1AyURJLKvR48kMVas4/%ED%83%80%EB%9E%98) 세 화면을 옮긴 정적 화면이다. 빌드 도구 없이 HTML · CSS · 바닐라 JS만 쓴다.

| 파일 | 피그마 프레임 | 하는 일 |
|---|---|---|
| `index.html` | — | 시작 화면. 실 그림 + 로그인·회원가입 (`assets/landing.css` · `assets/landing.js`) |
| `login.html` · `signup.html` | — | 로그인 · 회원가입 폼 (`assets/auth.css` · `assets/auth.js`) |
| `cases.html` | 01 내 사건 | 사건 카드 목록. 카드를 누르면 사건 상세로 간다 |
| `new.html` | 02 새 사건 등록 | 사건 유형 선택과 자료 올리기를 한 화면에서 |
| `case.html?id=…` | 03 사건 상세 · 타임라인 | 타임라인 · 인물 · 주장 대조 · 다음 행동 · 확인이 필요해요 |

앱 안쪽 화면의 브랜드(**타래**)를 누르면 시작 화면으로 나가고, 옆의 **내 사건**이 목록으로 간다.

## 실행

```bash
py web/serve.py
```

<http://localhost:8765>

`serve.py` 는 화면 파일을 주는 것과 함께 **사건 등록 API**(`/api/…`)를 연다. 새 사건 등록에서 올린 자료를
실제로 두 엔진에 넣어 정리한다. (윈도우 깃배쉬에서는 `python` 이 스토어 스텁이라 `py` 로 실행한다.)
`python -m http.server` 는 쓰지 않는다 — 캐시 헤더가 없어 **고친 HTML·CSS 대신 옛 화면을 보여 주고**, API 도 없다.

### 새 사건 등록이 하는 일

```
화면에서 고른 유형 · 사진 · OCR 결과 JSON · 메모 · 글 주소
  → POST /api/cases → local-cases/<id>/
  → research-engine run --ocr tesseract   (사진은 Tesseract 로 읽는다)
  → action-engine tools/export_web.py --result   (사건 하나의 화면 데이터)
  → case.html?id=<id>
```

| API | 하는 일 |
|---|---|
| `GET /api/status` | 사건 유형 목록(`research-engine/…/requirements/*.json` 에서 읽음) · OCR 준비 상태 |
| `GET /api/cases` · `GET /api/cases/<id>` | 이 컴퓨터에서 등록한 사건의 화면 데이터 |
| `POST /api/cases` | 사건 등록 (multipart: `case_type` · `title` · `file` · `modified` · `note`) |
| `POST /api/cases/<id>/files` | 자료를 더하고 사건 전체를 다시 정리 |

- **유형 목록을 화면에 적어 두지 않는다.** 엔진에 정의가 있는 유형만 고를 수 있다. 유형을 늘리려면 `requirements/` 에 JSON 을 더한다.
- **읽을 수 있는 자료만 받는다.** 사진(이미지)과 OCR 결과 JSON. PDF·음성은 읽는 경로가 아직 없어 목록에 넣지 않고 그 이유를 알린다. 글 주소는 글을 가져오지 못하므로 '본인이 적은 메모'로 들어간다.
- 등록한 사건과 올린 파일은 저장소 루트의 `local-cases/` 에만 남는다(gitignore). 어디로도 보내지 않는다. 엔진 실행 기록은 사건 폴더의 `run.log` 에 있다.
- 서버는 `127.0.0.1` 에만 열린다 — 이 컴퓨터 밖에서는 접속할 수 없다.
- **배포한 화면(GitHub Pages · Vercel)에는 이 서버가 없다.** 예시 사건만 보이고, 새 사건 등록은 "정리 서버에 연결되지 않았어요"라고 알리고 막는다. 등록을 배포 환경에서 돌리는 설계는 [`docs/등록-서버-배포-설계.md`](../docs/등록-서버-배포-설계.md).

### 사진을 읽으려면 (Tesseract OCR)

사진 없이 OCR 결과 JSON·메모만으로도 등록은 된다. 사진을 읽으려면 한 번 설치한다.

```bash
winget install --id UB-Mannheim.TesseractOCR -e
cd research-engine && uv sync --extra ocr
```

설치본에는 영어 데이터만 들어 있다. 한국어 데이터를 `~/.tarae/tessdata/` 에 받고 설치 폴더의 `eng`·`osd` 도 같이 둔다
(설치 폴더는 관리자 권한이 있어야 써진다).

```bash
mkdir -p ~/.tarae/tessdata
cp "/c/Program Files/Tesseract-OCR/tessdata/"{eng,osd}.traineddata ~/.tarae/tessdata/
curl -L -o ~/.tarae/tessdata/kor.traineddata https://github.com/tesseract-ocr/tessdata/raw/main/kor.traineddata
```

다른 위치에 두었다면 `TESSERACT_CMD`(실행 파일) · `TESSDATA_PREFIX`(데이터 폴더) 환경 변수로 알려 준다.
서버를 켜면 첫 줄에 `사진 읽기(OCR): 준비됨` 이 찍히는지 본다.

**OCR 정확도는 자료 모양에 크게 달려 있다.** 인쇄된 통지서는 대체로 읽지만 쉼표·마침표를 헷갈려 날짜(`2022. 9, 14.`)를
놓치기도 하고, 손글씨는 많이 틀린다. 틀리게 읽힌 줄은 엔진이 '읽히지 않은 부분'으로 올리고 되묻는다.

## 배포

| 어디 | 무엇이 도는가 |
|---|---|
| GitHub Pages | 화면만. `main` 에 `web/` 이 바뀌면 `.github/workflows/pages.yml` 이 올린다. 새 사건 등록은 막힌다 |
| Vercel | 화면 + **정리 함수**(`api/`). 새 사건 등록이 실제로 돈다. `main` 에 push 하면 프로덕션, PR 마다 미리보기 |

### Vercel 에서 새 사건 등록이 도는 방식

로컬 정리 서버(`serve.py`)는 사진을 Tesseract 로 읽고 사건을 `local-cases/` 에 쌓는다. Vercel 함수는 상태를 두지
않으므로 그 두 가지를 **브라우저로 옮긴다**.

```
사진 → tesseract.js 로 이 브라우저에서 읽음 (assets/browser-store.js)
OCR 결과 · 메모 → POST /api/analyze → 두 엔진을 돌려 화면 데이터만 돌려받음 (서버에 남지 않음)
사건 · 원본 사진 · 화면 데이터 → 이 브라우저의 IndexedDB
```

- `/api/status` 가 `mode: "browser"` 를 알리면 `app.js` 가 사건 조회·등록을 `browser-store.js` 로 보낸다.
  주소와 돌려주는 모양은 로컬 정리 서버와 같아서 화면 코드는 어느 쪽인지 몰라도 된다
- **등록한 사건은 그 브라우저에만 보인다.** 다른 기기·다른 브라우저에서는 안 보인다. 로그인이 없어도 남의 사건이 섞이지 않는다
- 사진 읽기는 처음 한 번 한국어 데이터를 CDN 에서 받는다. 시연 전에 그 브라우저로 한 번 등록해 두면 그 뒤로는 받지 않는다
- 함수(`api/analyze.py` · `api/status.py`)는 두 엔진을 설치하지 않고 저장소 안의 소스를 불러온다. 설치하는 것은
  루트 `requirements.txt`(두 엔진의 런타임 의존성)뿐이다
- 함수 본문 한도가 4.5MB 라 사진 원본은 보내지 않는다 — 보내는 것은 읽은 글자(OCR 결과 JSON)와 메모뿐이다

### Vercel 설정

저장소 루트의 `vercel.json`(프레임워크 없음 · 설치·빌드 없음 · `web/` 을 그대로 서빙 · `api/*.py` 함수)과 `.vercelignore`.
GitHub 저장소가 연결돼 있어 **`main` 에 병합하면 프로덕션이 자동으로 바뀐다.** CLI 로 올릴 때는 저장소 루트에서:

```bash
npx vercel login
npx vercel link --yes --project samjaegongsam
npx vercel deploy --dry     # 올라갈 파일 목록 — web/ · api/ · 두 엔진 src · export_web.py 뿐이어야 한다
npx vercel deploy           # 미리보기 (Vercel 로그인한 사람만 열림)
```

- **`.vercelignore` 는 전부 빼고 필요한 것만 다시 넣는다.** 저장소 루트의 `local-cases/` 에 화면에서 올린 피해 자료가
  있어서, 루트에서 CLI 로 배포해도 그런 파일이 올라가면 안 된다. 엔진은 `src/` 와 `tools/export_web.py` 만 — 테스트·픽스처·가상환경은 뺀다

## 데이터는 엔진에서만 온다

예시 사건은 `data/cases.js`(`window.TARAE_CASES`)에서, 등록한 사건은 위 API 에서 읽는다. 어느 쪽도 손으로 고치지 않고 엔진 출력으로 만든다.

```bash
cd action-engine
uv run python tools/export_web.py
```

`research-engine` 픽스처 → `build_card()` → 화면용 값. 엔진이나 픽스처를 고치고 다시 만들지 않으면 `test_커밋된_화면_데이터가_엔진_출력과_같다`가 실패한다.

- **다음 행동 카드의 무엇을·어디에·언제까지**는 지식베이스(`documents.json` · `deadlines.json`)에 있을 때만 채운다. 없으면 피그마 시안의 예시 문구 대신 "절차는 아직 확인 중"으로 둔다.
- 예시 사건 셋 중 **고소 사건(수사중지)** 만 절차가 채워진다(이의제기 기한 D-5). 나머지 둘은 다음 행동의 절차가 검수 전이라 비어 있는 것이 정상이다.
- 액션 이름(`ACT-신규정보제출` → "새로 확인된 정보를 수사기관에 제출")은 `export_web.py`의 `ACTION_LABELS`에 있다. 절차 문구가 아니라 행동의 이름만 적는다.

## 시안과 다른 곳

| 항목 | 이유 |
|---|---|
| 새 사건 등록의 자료 목록이 비어서 시작 | 시안은 자료 4개를 올린 상태를 그렸다. 실제 첫 화면은 빈 목록이다 |
| 가입해서 들어오면 사건 목록이 비어 있다 | 데모 사건은 데모 계정(`삼재공삼`)의 것이다. 새로 가입한 사람에게 보여주면 남의 사건을 자기 것으로 읽는다. 브라우저에 남기는 것은 아이디와 '데모인가' 하나뿐이고 비밀번호는 저장하지 않는다 |
| "정리 시작하기"가 실제로 정리한다 | 올린 자료를 정리 서버가 엔진에 넣고, 끝나면 그 사건 화면으로 간다. 서버가 없으면 이동하지 않고 이유를 알린다 |
| 유형 칩이 엔진이 다루는 유형뿐 | 시안의 '온라인 괴롭힘' · '폭행 · 상해' · '금전 피해' 는 엔진 정의가 없어 골라도 정리할 수 없다. '잘 모르겠어요'는 자료를 보고 유형을 제안하는 기능이 없어 뺐다 |
| 새 사건 등록에 '사건 이름 (선택)' | 비워 두면 유형과 등록한 날짜로 이름을 붙인다 |
| 인물 · 관계는 나무 모양 | 목록으로 늘어놓으면 누가 어디에 걸려 있는지 안 보인다. 사건을 뿌리로 두고 사람·기관·번호로 갈래를 친다. 엔진이 합치지 못한 '같은 대상일 수 있음'은 점선 상자로 붙인다 |
| 오른쪽 열은 탭마다 다름 | 다음 행동·확인이 필요해요는 타임라인에서만 쓴다. 인물·주장 탭에서는 그 화면에서 실제로 쓰는 것(자료 · 전문가 질문)만 둔다 |
| 인물 · 관계 / 주장 대조 탭을 엔진 데이터로 채움 | 피그마에 설계가 없지만 엔진이 이미 주는 값이다. 인물은 `timeline.entities`(역할 · 합치지 못한 '같은 대상일 수 있음' 링크까지), 주장 대조는 `analysis.slot_statuses` + 같은 항목의 `claims` — **기록 자료와 사람의 말을 구분해서** 나란히 놓는다 |
| 타임라인 한 줄은 날짜 · 점 · 짧은 제목 · 자세히 | 줄에 뱃지·출처를 다 붙이면 읽히지 않는다. 짧은 제목은 **원문에서 덜어내기만 한다** — 왼쪽 칸에 날짜가 있으니 앞머리 날짜를 떼고, 여러 문장이면 첫 문장만 남긴다(`_short_title`). 요약 문구를 새로 지어내지 않는다 |
| 「자세히」에 원문과 출처 | 상태(확인 완료 / 주장·미확인 / 불일치 / 날짜 확인 필요), 원문 전체, 어느 자료 몇 줄에서 왔는지와 인용문. 원본 사진 띄우기는 아직 연결되지 않았다고 적는다 |
| 타임라인 점 색 | 확인완료는 진회색, 확인되지 않은 것은 노랑, 어긋난 것은 빨강 |
| 타임라인에 "날짜 확인 필요" 배지 | 엔진이 날짜를 추정한 사건(`needs_confirmation`)을 알려준다 |
| 카드 선택 테두리는 마우스 올림·키보드 포커스에서 | 시안의 첫 카드 보라 테두리는 선택 상태를 보여준 것이다 |
| 내 사건 목록은 서류철(폴더) 카드 | 사건 하나가 자료를 담은 서류철이라는 걸 형태로 보여준다. 탭에 사건 유형을 적고, 앞면에 제목·진행 상태·확인 필요 수·다음 행동을 접지 않고 다 둔다 |
| 카드 색은 사건 유형이 정한다 | 실종=진보라 · 고소/수사중지=보라 · 재산범죄=연보라. 순서대로 색을 돌려 쓰면 사건이 하나 늘 때마다 색이 밀려서 '아까 그 진보라 사건'이 깨진다. 유형 딱지는 목록에 따로 붙이지 않는다 — 사건 이름이 이미 유형을 말하고 있어 겹쳐 보인다(상세 화면에는 있다) |
| 폴더 앞면의 D-day는 항상 보임 | 기한은 놓치면 되돌릴 수 없어서 펼치기 뒤에 숨기지 않는다 |
| 사건 상세의 머리말도 폴더 모양 | 목록에서 고른 폴더를 펼친 화면이라는 걸 보이게 한다. 탭에는 사건 유형을 적고, **목록에서 그 사건이 가졌던 색을 그대로 쓴다**(`toneOf`) |
| 새 사건 등록은 점선 빈 서류철 | 목록 끝의 점선 폴더(사건 등록)가 그대로 이어진다 |
| 사건 상세는 접을 것만 접는다 | 타임라인·인물·주장은 스크롤 없이 그대로 펼친다(자료가 많은 사건은 페이지가 길어진다). 대신 자료 목록·행동 설명은 팝업, 확인이 필요해요는 접어 둔다 |
| 「사진 찍기」가 카메라를 연다 | 노트북에서는 웹캠 미리보기를 띄워 찍고(`getUserMedia`), 휴대폰에서는 기본 카메라를 쓴다(`capture`). 권한을 막거나 카메라가 없으면 파일 선택으로 물러난다 |
| 「기억나는 내용을 직접 적기」가 동작 | 자료가 없어도 적어 둘 수 있다. '직접 적음'으로 들어가고 기록 자료와 구분해서 표시한다 |
| 자료 추가·직접 입력이 사건을 다시 정리함 | 등록한 사건의 「자료 추가하기」는 파일을 서버에 보내 사건 전체를 다시 정리한다. 「기억나는 일을 직접 추가」도 메모로 보내 다시 정리한다. 예시 사건은 자료를 더할 수 없고, 직접 입력은 **그 화면에만** 남는다고 창 안에 적는다 |
| 「전문가에게 물어볼 질문 만들기」가 실제로 동작 | 화면에 올라온 것(사건 요약 · 확인이 필요한 것 · 다음 행동)에서 질문지를 뽑아 팝업에 띄우고 복사할 수 있게 한다. 질문 틀은 갈래마다 정해 두고 내용은 엔진이 올린 문장을 그대로 넣는다. 법률 자문이 아니라 '물어볼 거리'라고 적는다 |
| 상단바에 메뉴 · 프로필 · 도움말 | 삼단 메뉴는 내 사건·새 사건 등록·자료 추가하기·도움말, 프로필은 내 정보·로그아웃. 도움말은 이 서비스가 무엇을 하고 **무엇을 하지 않는지**를 일상어로 적은 창이다 |
| 자료를 늘어놓지 않고 버튼 뒤에 둠 | 파일 이름이 화면 위쪽을 차지할 이유가 없다. 「+ 자료 추가하기」와 「첨부한 자료 N」 두 버튼을 오른쪽 열 맨 위에 두고, 목록은 팝업으로 연다 |
| 진행 단계 이름은 사건 유형마다 다름 | 엔진 `Stage` 는 여섯 가지(발생·송금·신고·접수·수사·결과)로 유형을 가리지 않는다. 수사중지 사건이 '결과'로 끝나면 사건이 끝난 줄 안다 — 실제로는 **중지**이고 뒤에 되살릴 길이 남아 있다. `export_web.py` 의 `STAGE_TRACKS` 가 화면 이름만 바꾼다(실종: 발생·신고·수사·**중지**·재수사 / 수사중지: 고소·접수·수사·**중지**·재개). 엔진 코드는 건드리지 않는다 |
| 진행 단계는 흰 굵은 선 + 현재 마디가 빛남 | 어디까지 왔는지를 색 대비로 먼저 읽히게 한다. 남은 구간은 흐린 흰색 |
| 1024px 이하에서 한 열로 접힘 | 시안은 1440px 데스크톱. 1차 사용자가 휴대폰을 쓴다 |

## 로고

`assets/logo-original.png` 가 손으로 그린 원본(흰 배경 · 검은 그림)이다. 화면에 쓰는 두 파일은 여기서 만든다.

| 파일 | 어디에 |
|---|---|
| `assets/logo.png` | 밝은 화면 — 앱 상단바, 파비콘 |
| `assets/logo-light.png` | 어두운 화면 — 시작 · 로그인 · 회원가입. **선만 흰색으로 남기고 줄무늬는 뚫는다** — 원판을 칠하면 어두운 바탕 위에서 덩어리로 보인다 |

만드는 법은 `tools/make_logo.py` 에 있다. 바깥 흰 배경만 투명하게 하고(원 안쪽 흰 줄무늬는 그림의 일부라 남긴다) 검은 부분에 색을 올린다. 원본을 다시 그리면 이 스크립트를 다시 돌린다.

```bash
py web/tools/make_logo.py
```

글꼴은 두 가지다. 본문은 **IBM Plex Sans KR**(`--font`), 이름 '타래'만 **Gugi**(`--font-brand`)를 쓴다 — 붓 느낌이라 실타래라는 이름과 맞고, 굵기가 하나뿐이라 400 으로 쓴다. 바꾸려면 `tokens.css` 의 `--font-brand` 한 줄과 각 HTML 의 구글 폰트 주소만 고치면 된다.

토큰(`assets/tokens.css`)은 피그마 변수 이름과 1:1이다(`bg/canvas` → `--bg-canvas`). 아이콘은 피그마 에셋 원본(`assets/icons/`)이다.
