# 새 사건 등록을 배포 환경에서 돌리기 — 설계안

> 상태: **제안 · 결정 필요** (2026-09-18)
> 지금 Vercel·GitHub Pages 에는 화면(`web/`)만 올라가 있다. 새 사건 등록은 이 컴퓨터의 정리 서버
> (`web/serve.py`)가 있어야 돌고, 배포된 화면에서는 "정리 서버에 연결되지 않았어요"로 막힌다.
> 이 문서는 등록까지 배포 환경에서 돌리려면 무엇을 바꿔야 하는지, 무엇을 정해야 하는지를 적는다.

## 1. 지금 구조가 Vercel 에서 막히는 곳

| 지금 (`web/serve.py`) | Vercel 에서 | 바꿀 것 |
|---|---|---|
| 두 엔진을 `uv run` 하위 프로세스로 부른다 | 함수 안에 `uv` 가 없다 | 함수에서 두 엔진을 **import 해서 직접** 부른다. 둘 다 순수 파이썬(pydantic 등)이라 Python 함수 번들 한도(500MB) 안에 든다 |
| 사진을 Tesseract **실행 파일**로 읽는다 | 일반 Python 함수에는 없다 | §3 OCR 선택지 |
| 사건을 `local-cases/` 디스크에 쌓는다 | 함수는 상태가 없다 — 요청이 끝나면 파일이 사라진다 | §4 저장소 선택지 |
| 한 번에 40MB 까지 받는다 | 함수 요청·응답 본문은 **4.5MB** 까지 | 사진은 함수를 거치지 않고 저장소로 **직접** 올린다 |
| `127.0.0.1` 에만 열려 있다 | 공개 주소다 | §2 로그인 — **이게 없으면 배포하면 안 된다** |
| 정리 한 번에 2초 남짓 | 함수 최대 실행 300초(Hobby) | 문제 없다 |

## 2. 가장 먼저: 진짜 로그인

지금 로그인은 브라우저 `localStorage` 안에서만 아이디를 확인하는 **흉내**다(`web/assets/auth.js`). 서버는
누가 요청하는지 모른다. 이 상태로 등록 API 를 공개 주소에 열면 `GET /api/cases` 한 번으로 **모든 사람의 사건과
원본 사진**이 보인다. 올라오는 것은 실종·미제 사건 피해 가족의 통지서·진술서다.

필요한 것:

- 서버가 확인하는 로그인 (세션 또는 토큰)
- 모든 사건에 **소유자**를 붙이고, 읽기·쓰기·원본 보기마다 소유자를 확인
- 탈퇴·사건 삭제 시 원본까지 지우는 경로

정적 HTML 화면에 그대로 붙일 수 있는 선택지:

| | 장점 | 단점 |
|---|---|---|
| **Supabase Auth** | 저장소(Postgres·Storage)까지 한곳. Row Level Security 로 "내 사건만"을 DB 가 막는다 | 서비스가 하나 더 생긴다 |
| **Clerk** | 로그인 화면이 완성돼 있다 | 저장소는 따로 골라야 한다 |

## 3. 사진 읽기 (OCR)

엔진은 이미 **OCR 결과 JSON**(`OcrDocument` — 줄·상자·신뢰도)을 입력으로 받는다. 사진을 어디서 읽느냐만 정하면 된다.

| | 어디서 읽나 | 자료가 밖으로 나가나 | 비용 | 정확도 |
|---|---|---|---|---|
| **A. 브라우저 OCR (tesseract.js)** | 사용자 기기 | 읽는 단계에서는 안 나간다 | 없음 | 지금 Tesseract 와 같은 엔진이라 같은 수준. 한국어 데이터를 처음 한 번 내려받는다 |
| B. 컨테이너 함수 (`Dockerfile.vercel` + Tesseract) | Vercel 함수 | Vercel 안 | 함수 CPU 시간 | A 와 같다 |
| C. 외부 OCR API (CLOVA OCR · Google Vision · Claude) | 외부 서비스 | **나간다 — 동의 필요** | 건당 과금 | 손글씨·흐린 사진에서 훨씬 낫다 |

**추천: A.** 서버가 사진을 읽을 일이 없어지고, 함수에는 OCR 결과 JSON(수십 KB)만 가므로 4.5MB 제한도 비껴 간다.
음절마다 띄어 나오는 한국어 결과를 붙이는 `join_words`(`research-engine/…/ingest/ocr.py`)는 서버에서 그대로
쓰도록 **단어 상자 단위**로 보낸다. 정확도가 모자란 자료만 사용자가 동의하면 C 로 다시 읽는 선택지를 나중에 붙인다.

## 4. 저장소

| 무엇 | 선택지 |
|---|---|
| 원본 사진 ("원본 보기") | Vercel Blob **private** 저장소(읽기에 인증 필요) · 또는 Supabase Storage 비공개 버킷 |
| 사건 메타·화면 데이터(`meta.json` · `view.json`) | Supabase Postgres · 또는 Vercel Marketplace 의 Postgres/Redis |

피해 자료 원본이므로 **public 저장소는 쓰지 않는다**(주소만 알면 누구나 본다).
로그인을 Supabase 로 정하면 저장도 Supabase 로 두는 것이 가장 단순하다.

## 5. 코드 구조

- `web/serve.py` 의 등록 로직(`add_uploads` · `build_case_input` · `analyze`)을 저장 방식과 떼어 **공용 모듈**로 뺀다.
  로컬 서버(디스크)와 Vercel 함수(저장소)가 같은 로직을 쓴다
- 엔진 호출을 `uv run` 에서 import 로 바꾼다. `build_view` 는 지금 `action-engine/tools/export_web.py` 스크립트 안에
  있어 패키지 밖이다 — `action_engine` 패키지 안으로 옮긴다
- Vercel 함수는 `api/` 아래 Python 파일. 두 엔진은 저장소 안의 경로로 설치한다(`./research-engine` · `./action-engine`).
  지금 `.vercelignore` 는 `web/` 만 올리므로 `api/` 와 두 엔진 폴더를 다시 넣어야 한다 — `local-cases/` 는 계속 뺀다
- 화면은 API 주소가 상대 경로(`api/…`)라 그대로 쓴다

## 6. 순서

1. 로그인·사건 소유 (§2) — 이것 없이 등록 API 를 공개하지 않는다
2. 저장소 (§4)
3. 등록 로직 공용화 + 엔진 import (§5)
4. 브라우저 OCR (§3 A)
5. 원본 사진 직접 업로드 + 원본 보기를 인증 거쳐 내주기
6. 보관 기간 · 사건 삭제 버튼 · 올리기 전 동의 문구
